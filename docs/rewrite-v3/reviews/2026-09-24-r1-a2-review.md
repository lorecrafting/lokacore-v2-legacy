## 5. Rulings on the eight known issues

**1. `commit_unknown` exercises only a COMMIT that succeeded.** Acceptable
for A2, required in A3. The code that resolves an unknown outcome from
storage alone is the same on both hosts as the code that recovers from
`raise`, `io_error` and `kill` at `in_persistence` (server `rebuild/1` and
`fault_response/2`; phone `DurableHost` constructor plus the receipt lookup in
`judge`), and those cases show the "not committed" answer (no receipt row →
`rolled_back`, `delivery: new`, no RNG advance) in 54 server records and 3 per
phone. What is not shown is a COMMIT that was issued and failed. A3 must add
it on the phones, where it is injectable: in `journal_mode=delete` the main
file is written at COMMIT, so clamping `max_page_count` immediately before
`COMMIT` with the result discarded yields a real failed COMMIT under the fence.
On the server (WAL) record it as not deterministically injectable and covered
by `kill` at `in_persistence`, unless a deterministic COMMIT failure is found.

**2. Duplicate delivery while views/choices are stale is not a fault case.**
A3. The durable hosts already replay the A1 sequences: 37 of the 52
`world.run` lines on the phones contain a repeated request id, 16 of them with
a `view` on the repeat, and every line is byte-identical to the model. That is
the semantic path without an injected fault. The envelope sentence sits in §9
and A3's row says "all fault points", so A3 must schedule a fault at each point
on a stale-view duplicate.

**3. Server resets `published`; phone persists an outbox.** Acceptable for
A2 as documented (F4); must be unified or contractually defined before A3.

**4. Server SQLite 3.53.4 versus phones 3.50.3.** Acceptable. The setup's
`toolchain.sqlite` is the phone engine (F12 of the setup review), and the
server engine is a declared A2 result item; it is recorded with version,
source id, compile options, `exqlite` 0.40.0, `force_build` and the compiler
in `sqlite-identity.json` and `host-facts.txt`. Required for A3/A4: the result
manifest needs a server SQLite field distinct from `toolchain.sqlite`, since
the template has none.

**5. Not byte-identical APKs and iOS binaries.** "Repeatable builds" is
satisfied for A2. Envelope §10 asks for repeatable build steps; every byte
that carries semantics (Metro bundle, Hermes bytecode, source maps, every APK
entry, native libraries, Mach-O contents after signature removal) reproduces
across two clean builds on both platforms, and the two residual regions are
signing-time material (AGP dependency-info block; Apple code signatures) plus
one DWARF byte, each located and retained. The result manifest should pin the
bundle/bytecode/library hashes as the app identity rather than the whole APK
hash, which is not stable by design.

**6. Workflow now passes `-PreactNativeDevServerIp=localhost` and root
`buildEnvironment`; the APK differs from the setup probe APK.** No renewed
setup review. The A2 digest binds toolchain versions and the lock index, and
