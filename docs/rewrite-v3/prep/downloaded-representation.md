## Concrete representation and shipped surface

[The retained sample](downloaded-payload.sample.json) describes the contemplated
bytes: immutable first-party story definitions, identifiers, choices, typed
consequences and presentation assets. It is intentionally marked as a
pre-production policy specimen, NOT a compiler output or an accepted R1 fixture.
The four places illustrate content expressiveness, not a change to the 57-room
chapter or permission to start R6P.

The proposed installed app contains all operation implementations, definition
validation, deterministic evaluator, native integration, save/receipt authority
and the renderer. Downloaded content refers to that closed/versioned feature
set. It cannot install JS/TypeScript modules, BEAM bytecode, native libraries,
DEX/JAR, arbitrary shaders, a new opcode evaluator, dynamic imports or `eval`.
New engine capability requires an app/runtime release and compatibility review.

Loading a definition is not authority to mutate: the selected Story/Realm owner
still admits an invocation, evaluates a proposal and commits once. Content gets
no direct native API, account, filesystem, network, database or platform-privilege
bridge. Engine-owned operations translate data into bounded proposals; guards,
conflicts, budgets and capability locks still apply. The app must reject unknown
operations/profiles rather than execute fallback source. These are proposed
release boundaries to verify in the actual app, not capabilities implemented by
this sample or a claim that JSON is inherently harmless.

## Current official policy check

Checked 2026-09-22 (Hawaii; 2026-09-23 UTC). Sources:
[Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
and [Google Play Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en).

| Source | Material constraint | Application to the proposed representation |
|---|---|---|
| Apple 2.5.2 | Downloaded/executed code that changes app features/functionality is restricted. | Calling authored behavior “declarative data” does not settle its classification. Document exactly which shipped features the payload composes. |
| Apple 4.7, especially 4.7.2–5 | Certain non-embedded software is permitted subject to additional native-API, consent, indexing/link and age-related requirements. | Do not assume a story interpreter automatically qualifies or is exempt. Determine whether this section applies to the exact app and its content surface. |
| Apple submission guidance | Supply full review access and explain non-obvious features. | Prepare a build and sample download demonstrating both terminal consequences, denied unsupported content and the entire installed API surface. |
| Google Play | Outside-Play executable downloads are restricted; interpreter exceptions are conditional and interpreted content must not facilitate violations. | No downloaded native/DEX/JAR components or direct Android API access; review actual runtime behavior, not just file extensions. |

## Bounded risk disposition and next evidence

The sample has a **narrow technical surface but unresolved distribution
classification risk**. Recommendation: retain the disposable feasibility scope;
do not scale expensive production content investment on an assumption of store
acceptance. PREP-03 can proceed in parallel with R1, but its investment disposition
is required before R1-A5/R2 as specified in the work package. It does not waive
PREP-02 and does not favor any candidate; ADR-068 sets the test order C, B, A.

The owner should record one explicit disposition against the exact proposed
payload/build: accept the documented investment risk with a retained review
plan, revise the payload/surface, or obtain platform clarification before scaling.
The record remains pending here; this recommendation is not owner approval.
A bounded fallback to evaluate is bundling the initial chapter definitions with
the reviewed app release, rather than adding a generalized downloadable software
platform. That fallback is also not a guarantee of approval or an authorization
to change the product contract silently.

Before public launch, repeat the review against current policy and the actual
binary, downloadable bytes, exposed APIs and review notes. Include account access
and all download routes, not only the in-bundle demo. Store classification and
release acceptance remain separate from deterministic conformance, local SQLite
atomicity, physical-device measurements and owner architectural approval.
